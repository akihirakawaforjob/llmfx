# llmfx

ダウ理論の「転換」を売買根拠とする FX 自動売買システム。売買判断は
ルールベースで決定的に行い、Claude はその周辺(見送り判断・所感の記録・
改善提案)を担当します。

現在のマイルストーンは **バックテスト + ペーパー取引** までです。
実弾発注のアダプタ(OANDA)は同梱していますが、既定では動きません。

---

## 要件と実装の対応

| 要件 | 実装 | 該当箇所 |
| --- | --- | --- |
| 1. ダウ転換でエントリー | 確定済みスイングを終値でブレイクした瞬間を検出 | `llmfx/domain/dow.py` |
| 2. 損切りは転換前の最高値/最安値 | 転換前の極値 + ATR バッファ | `llmfx/domain/dow.py` `_stop_basis` |
| 3. RR が 1/2 を上回る場合のみ | `reward / risk >= 2.0` を満たさないシグナルは破棄 | `llmfx/domain/strategy.py` |
| 4. 月利 1.4 倍を目指す | 必要リスク率の逆算 + 破産確率のモンテカルロ | `llmfx/domain/risk.py` |
| LLM に所感を書かせる | エントリー時・決済時の構造化ノート | `llmfx/llm/journalist.py` |
| LLM に改善提案を出させる | 記録 + 統計から改善レポート生成 | `llmfx/journal/review.py` |

## セットアップ

```bash
pip install -r requirements.txt
cp .env.example .env     # API キーを使う場合のみ編集
```

Python 3.10 以上が必要です。**API キーが無くても全機能が動きます**
(LLM 層が自動的に無効化され、ルールベース部分だけで動作します)。

## 5 分で試す

```bash
# 1. 合成データを作る(API 不要)
python -m llmfx.cli data synth --out data/sample.csv --count 20000

# 2. バックテスト + レポート生成
python -m llmfx.cli backtest --config configs/default.yaml \
    --data data/sample.csv --journal data/journal.sqlite

# 3. 目標月利の実現可能性を検証(バックテストの実測値を入れる)
python -m llmfx.cli target --win-rate 0.35 --win-r 2.3 --loss-r 0.7 \
    --trades-per-month 17

# 4. ペーパー取引(CSV を時系列で再生)
python -m llmfx.cli paper --config configs/default.yaml \
    --replay data/sample.csv --journal data/paper.sqlite

# 5. 記録からレビューを生成(--llm で改善提案が付く)
python -m llmfx.cli review --journal data/paper.sqlite --out out/review.md
```

> ⚠️ 合成データは動作確認専用です。そこで出た成績には一切意味がありません。
> 戦略の評価は必ず実データ(`llmfx data fetch`)で行ってください。

## 実データを使う

データの入手方法は 2 通りあります。どちらでもバックテスト以降は同じです。

### A. 楽天 MT4 など、MT4 / MT5 から CSV をエクスポートする

MT4 の「ツール → ヒストリーセンター」で通貨ペアと時間足を選び、
`エクスポート` で CSV を保存してから取り込みます。

```bash
python -m llmfx.cli data import-mt4 --in ~/Downloads/USDJPY15.csv \
    --out data/usdjpy_m15.csv --server-tz-offset 2
```

`--server-tz-offset` は **データの時刻が UTC から何時間ずれているか**。
MT4 のサーバ時刻は業者ごとに GMT+2 / GMT+3 などへずれており、UTC ではありません。
取り込み後に表示される期間と足の間隔が想定どおりか確認してください。

ヘッダの有無、カンマ / タブ区切り、日時が 1 列か 2 列か、末尾の余分な列は
自動で判定します。

### B. OANDA の API から取得する

```bash
export OANDA_API_TOKEN=...      # デモ口座のトークン
export OANDA_ACCOUNT_ID=...
export OANDA_ENV=practice

python -m llmfx.cli data fetch --instrument USD_JPY --granularity M15 \
    --count 50000 --out data/usdjpy_m15.csv
```

### どちらの場合も

```bash
python -m llmfx.cli backtest --config configs/default.yaml --data data/usdjpy_m15.csv
python -m llmfx.cli diagnose --config configs/default.yaml --data data/usdjpy_m15.csv
```

## 売買ロジック

### ダウ転換の定義

```
上昇トレンド = 高値切り上げ(HH)かつ安値切り上げ(HL)
下降トレンド = 高値切り下げ(LH)かつ安値切り下げ(LL)

強気転換: 下降トレンド中に、確定済みの直近スイング高値を終値で上抜け
弱気転換: 上昇トレンド中に、確定済みの直近スイング安値を終値で下抜け
```

上昇トレンド中の高値更新は「継続」であり転換ではないため、シグナルを
出しません。同じスイング水準で 2 度シグナルが出ることもありません。

### 先読みを持ち込まないための規律

スイングは左右 N 本のピボットで確定するため、**確定は常に N 本遅れます**。
このずれを無視すると、バックテストの成績はいくらでも良くできてしまいます。

- スイングは `confirmed_index <= 現在バー` のものだけを参照する
- シグナル判定は確定足の終値のみ。既定の約定は翌足の始値
- 同一足で損切りと利確の両方に触れた場合は、必ず損切りが先に約定した扱い
- 逆指値・成行にはスリッページを乗せ、指値には乗せない

`tests/test_backtest.py::test_no_lookahead_truncating_data_does_not_change_past_trades`
がこれを検証しています(データを途中で打ち切っても、それ以前のトレードが
1 件も変わらないこと)。

## RR フィルタの幾何学 — 実装で最も重要な設計判断

要件 2(損切りは転換前の極値)と要件 3(RR ≥ 2.0)は、そのまま組み合わせると
**構造的にほとんどのエントリーを弾きます**。理由は幾何学的なものです。

```
        H ← 直近スイング高値(ここを上抜けて転換)
       ╱ ╲
      ╱   ╲          リスク = (H − L) + バッファ   ← 波 1 本分の全長
     ╱     ╲
    ╱       L ← 転換前の最安値(損切りの根拠)
```

損切りを L に置く以上、リスク幅は必ず「直前の波の全長」になります。
したがって利確目標は **波 2 本分より遠く** ないと RR 2.0 に届きません。

実測(合成データ 20,000 本、254 回の転換):

| 利確目標の決め方 | RR 中央値 | RR ≥ 2.0 の割合 |
| --- | ---: | ---: |
| `structure`(最も近い抵抗/支持) | 0.55 | **1.2%** |
| `measured_move`(波 1 本分の投影) | 0.85 | ~2% |
| `trend_origin`(反転させたトレンドの起点) | **1.98** | **49.4%** |

`structure` や `measured_move` を目標にすると、ほぼすべてのシグナルが
RR フィルタで消えます。そこで既定を `trend_origin` にしました。これは
ダウ理論としても整合的です — 下降トレンドが終わったなら、価格はその
下降が始まった地点へ向かって戻る、という読みが損切り幅と釣り合います。

**目標を RR が通るまで選び直すことはしません。** それは利確位置の後付けで
あり、フィルタの意味を失わせます。設定した順に「水準を出せた最初の戦略」を
採用し、その結果の RR で判定します。

自分のデータでこの分布を確認するには:

```bash
python -m llmfx.cli diagnose --config configs/default.yaml --data data/your.csv
```

## 月利 1.4 倍(+40%)について

これは非常に高い目標です。本システムは目標を隠さず、**達成に必要な条件と
その代償を数値で提示します**。`backtest` のレポート末尾と `target` コマンドの
出力がそれです。

計算モデル(固定比率ベット):

```
勝ち: 資産 × (1 + f × R_win)      f      = 1 トレードあたりリスク率
負け: 資産 × (1 − f × R_loss)     R_win  = 平均利益(R 倍数)
                                  R_loss = 平均損失(R 倍数)
月利 = exp(N × E[log 成長率])      N      = 月間トレード数
```

この式を f について二分法で解き、得られたリスク率で 12 ヶ月・20,000 経路の
モンテカルロを回して破産確率と最大ドローダウンを出します。

出力の読み方:

- **`到達不能`** — ケリー基準(対数成長が最大になる点)で張っても目標に
  届かない状態。この場合、**リスクを上げても届きません**。勝率・平均 R・
  トレード頻度のいずれかを改善する以外に道はありません。
- **必要リスク率 > ケリー基準** — リスクを上げるほど期待成長率が *下がり*、
  破産確率だけが上がる領域。警告が出ます。
- **破産確率・最大ドローダウン** — 目標を達成する経路でも、途中で資産が
  半分近くまで削られるのが普通です。この振れ幅に耐えられるかは、
  資金を入れる前に判断してください。

参考: 勝率 35%・平均利益 2.3R・平均損失 0.7R・月 17 トレードという成績なら、
月利 1.4 倍に必要なリスク率は約 6.6%、破産確率 2.2%、しかし
**最大ドローダウンの中央値は 44%** です。

## LLM 層(Claude)

売買判断そのものは LLM に渡しません。判断が非決定的になるとバックテストと
実運用が乖離し、検証が成り立たなくなるためです。役割は 3 つに限定しています。

### 1. 拒否権(gate)

ルールが出したエントリーを見送るかどうかだけを決めます。エントリーを
新しく作ることはできません。プロンプトでは「迷う程度なら通す」ことを
明示しています — 過剰な見送りはサンプル数を削り、検証を壊すためです。

### 2. 所感の記録(journalist)

- **エントリー時**: 仮説、構造の読み、否定条件、注目点、確信度
- **決済時**: 何が起きたか、仮説は正しかったか、原因の切り分け、教訓、調整案

決済時の原因分析は「仮説の誤り / 執行の問題 / 分散」の 3 つに切り分けます。
3 つ目を 3 つ目として認識させることが重要です。正しいトレードでも負けるため、
単発の負けをすべて改善対象にするとルールが壊れます。

### 3. 改善提案(review)

蓄積した記録・成績統計・目標達成に必要な条件を渡し、次に試す変更を
提案させます。1 回のレポートで提案するのは 3 件までに制限しています
(同時に複数変えると何が効いたか分からなくなるため)。

```bash
python -m llmfx.cli review --journal data/journal.sqlite --days 30 --llm --out out/review.md
```

### 実装上の配慮

- **プロンプトキャッシュ**: 売買ルールの説明は毎回同一なので `cache_control`
  の対象。可変情報(時刻・価格)は必ず user 側に置き、キャッシュを壊さない
- **応答キャッシュ**: 同じ入力なら同じ出力になるよう SQLite に保存。
  バックテストの再実行結果が変わらない
- **構造化出力**: `output_config.format` で JSON Schema を強制。全項目必須・
  追加プロパティ禁止
- **拒否応答**: `stop_reason == "refusal"` を必ず確認してから content を読む
- **障害時**: `fail_open`(既定 true)ならルール判断を優先して通す。
  高リスク設定では false にして「判断できないときは見送る」

## 設定

`configs/default.yaml`(保守的)と `configs/aggressive.yaml`(高リスク)を
同梱しています。設定のタイポは黙って無視されず、エラーになります。

主要なパラメータ:

| キー | 意味 |
| --- | --- |
| `swing.left` / `right` | ピボット確定に必要な左右の本数。小さいほど高頻度・高ノイズ |
| `swing.min_swing_atr` | スイングとして認める最小値幅 |
| `entry.min_rr` | **要件 3。緩めないこと** |
| `entry.stop_basis_mode` | `trend_extreme`(要件どおり)/ `recent_swing`(浅い損切り) |
| `entry.target_strategies` | 利確目標の決定順。既定 `trend_origin` |
| `risk.risk_per_trade` | 1 トレードあたりリスク率 |
| `risk.max_daily_loss` | 当日損失の上限。超えたら新規停止 |
| `risk.max_drawdown_stop` | 累計 DD の上限。超えたら全停止(キルスイッチ) |
| `execution.entry_mode` | `next_open`(現実的)/ `close`(楽観的) |

## テスト

```bash
python -m pytest -q
```

97 件。重点を置いているのは次の性質です:

- スイングは右 N 本を見終わるまで確定しない(先読み防止)
- データを打ち切っても過去のトレードが変わらない(先読み防止)
- 全シグナルが `min_rr` を満たす(要件 3)
- 損切りが必ず建値の逆側にある(要件 2)
- 逆算したリスク率で本当に目標成長率になる(検算つき)
- API キーが無くても例外で止まらない

## ディレクトリ構成

```
llmfx/
  domain/          売買ロジック(外部 I/O に依存しない)
    swings.py      ピボット検出(逐次・確定遅延あり)
    dow.py         トレンド状態機械とダウ転換検出
    targets.py     利確目標の決定
    strategy.py    3 要件を束ねたシグナル生成
    risk.py        サイジング・リスク制限・目標月利の逆算
  data/            OANDA / CSV / MT4 エクスポート / 合成データ
  execution/       約定モデル・ブローカー・実行ループ
    fills.py       バックテストとペーパー取引で共有する約定判定
  backtest/        イベント駆動バックテストと成績評価
  llm/             Claude クライアント・拒否権・所感
  journal/         SQLite 記録と改善レポート
  cli.py
```

`execution/fills.py` をバックテストとペーパー取引で共有しているのは意図的です。
両者で約定ロジックが分岐すると、検証した挙動が実運用で再現しないという
最悪の形で裏切られます。

## 制約と未検証の部分

- **OANDA への実接続は未テスト**です。この開発環境から API 資格情報に
  アクセスできないため、`llmfx/data/oanda.py` と `OandaBroker` は
  仕様に沿って実装してありますが動作確認ができていません。
  初回はデモ口座かつ最小ロットで確認してください
- **本番口座はブロックしています**。`OANDA_ENV=live` かつ `allow_live=True`
  の両方を明示しない限り動きません
- **楽天 FX には Python から直接発注できる公開 API がありません**。楽天で自動売買する場合、正規ルートは MT4 の EA(MQL4)です。
  将来的に実弾へ繋ぐときは、判断を Python 側に残したまま MT4 には発注だけさせる
  ブリッジ構成を想定しています(戦略ごと MQL4 へ移植すると LLM 層が使えなくなるため)
- **同時保有は 1 銘柄・1 建玉**です。複数通貨ペアの同時運用は未実装
- **スワップポイントは未計上**です。日をまたぐポジションでは実際の損益と
  ずれます
- 合成データでの成績は戦略の有効性を何も示しません
